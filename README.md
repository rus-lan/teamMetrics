# team-metrics

Строит один самодостаточный HTML-отчёт по метрикам спринта и команды на основе данных Jira
(и опционально GitLab). Два CLI на чистом stdlib Python 3.9+ — ни одной сторонней зависимости,
никакой сборки, никакого сервера. На выходе — один файл `.html` без единой внешней ссылки,
который открывается через `file://` вечно, хоть офлайн.

Это **Python-порт двух внутренних инструментов**: движка спринт-метрик Jira
(`internal/app/board/{translate,service,report,forecast}.go`) и скилла персональных/инженерных
метрик на данных GitLab. Цифры, пороги и даже особенности (разное значение одних и тех же полей на
разных вкладках, «сдвиг на единицу» между `throughput_items` и `delivered_items`, точная арифметика
перцентилей/гистограммы в прогнозе) воспроизведены **намеренно** — это честный порт, а не редизайн.
Построчные ссылки на источник и решения по вёрстке (пороги статусов, направление дельт, четыре
состояния пустого значения) живут в docstring'ах модулей, которые ставятся вместе с инструментом —
`metrics.py`, `personal_metrics.py`, `engineering_metrics.py`, `forecast.py`, `burndown.py`,
`render_html.py` — а не во внутренних `.research/*/SPEC.md`, которые в этот репозиторий не входят
(`.gitignore`) и с релизом не поставляются.

Как запускать это как навык (skill) агента — см. [`SKILL.md`](./SKILL.md). История версий — в
[`CHANGELOG.md`](./CHANGELOG.md).

## Что нужно, прежде чем начинать

1. **Python 3.9 или новее** — только стандартная библиотека, ставить ничего не нужно.
2. **Personal Access Token в Jira** (обязательно). Инструмент шлёт его как
   `Authorization: Bearer <token>` — это токен формата Jira Server/Data Center, а не
   почта+API-токен Jira Cloud (Basic Auth). Получить: аватар профиля в правом верхнем углу →
   **Personal Access Tokens** (в русской локализации — «Личные токены доступа») → **Create token**.
   Если ваша Jira — облачная (`*.atlassian.net`) и токенов такого вида в профиле нет, сначала
   уточните у администратора Jira, включена ли поддержка PAT — без неё это конкретный инструмент
   не подключится.
3. **Токен GitLab со scope `read_api`** (опционально — без него отчёт всё равно строится, просто
   без вкладок «05 Люди — сравнение», «06 Люди — динамика» и «07 Инженерия»). Получить: аватар профиля → **Edit profile** →
   **Access Tokens**, поставить галку `read_api`, создать.
4. Знать **имя или id спринта** в Jira, по которому нужен отчёт (`--sprint-names "Sprint 42"` или
   `--sprint-ids 4821`).

Ни один из токенов никогда не хранится в конфиг-файле — только в переменных окружения (подробнее
ниже).

## Прежде чем указывать инструмент на прод

Независимый аудит безопасности инструмента подтвердил главное: **инструмент структурно не может
писать ни в Jira, ни в GitLab** — только читает. Но у чтения тоже есть последствия, три из них
стоит знать заранее, а не обнаружить постфактум.

**PAT в Jira Server/Data Center нельзя выпустить read-only.** По документации Atlassian такой
токен «соответствует текущему уровню прав пользователя» — отдельного селектора scope для PAT в
Jira Server/DC нет. Значит токен несёт все права своего аккаунта, включая запись, даже притом что
сам этот инструмент вызывает только read-эндпоинты. Утечка такого токена — это утечка полного
доступа аккаунта, а не «доступа только на чтение отчётов». Единственная надёжная защита — на
уровне аккаунта, а не токена: заведите отдельного технического пользователя с правом Browse
Projects только на нужные проекты и выпускайте PAT из-под него, а не из-под личного аккаунта с
продовыми правами.

**Прокси в окружении увидит токен.** Инструмент использует `urllib` с настройками по умолчанию —
значит, уважает `http_proxy`/`https_proxy`, если они заданы: заголовок `Authorization: Bearer
<token>` пройдёт через то, что за этими переменными стоит. В корпоративной сети это обычно и есть
смысл прокси, но прежде чем указывать инструмент на прод, проверьте, куда именно смотрят ваши
`http_proxy`/`https_proxy` в этом окружении. Флаг `--no-proxy` у `check`/`run` отключает прокси на
уровне самого инструмента — для запросов и к Jira, и к GitLab — не трогая переменные окружения
самого процесса.

**GitLab-scope `read_api` — этого достаточно, но не единственное условие.** Каждое обращение
инструмента к GitLab — простой GET-запрос, ни один эндпоинт не требует полного scope `api`, так
что `read_api` — правильный, минимальный выбор. Но для приватных проектов одного scope мало:
аккаунту, из-под которого выпущен токен, дополнительно нужна роль в самом проекте — как правило,
Reporter и выше (точная минимально достаточная роль для эндпоинта job'ов пайплайна в документации
GitLab не зафиксирована, поэтому это «как правило», а не гарантия). Без роли в проекте токен с
формально верным `read_api` всё равно ничего не увидит.

## Объём запросов — не указывайте на прод вслепую

Для одного `run` измеренный (не оценочный) худший случай:

- **Jira**: около **12** последовательных запросов.
- **GitLab**: около **1660** запросов при конкурентности 8, до **~6600** с учётом ретраев — это
  из-за пофайлового обхода по каждому MR и по каждому пайплайну отдельным запросом.

Прежде чем указывать инструмент на боевые Jira/GitLab — особенно с большой командой или большим
числом проектов GitLab, — снижайте нагрузку поэтапно, а не сразу полным `run`:

1. Первый прогон — с `--no-gitlab` (только Jira, ~12 запросов): убедитесь, что база работает.
2. Затем добавьте GitLab, но с `--no-personal` (снимает около **880** самых тяжёлых, по-MR,
   запросов) — проверьте вкладку «07 Инженерия» отдельно. На этом шаге можно дополнительно передать
   `--light` — экономит ещё около **1200** запросов из ~1660 в среднем `run`, ценой того, что
   связанные метрики станут «нет данных» вместо реальных значений.
3. И только потом — полный `run` без флагов (или всё ещё с `--light`, если тяжёлые поля пока не
   нужны).

Отдельные флаги для точечного отключения самых тяжёлых обходов GitLab — по MR и по пайплайнам —
уже есть, каждый можно включать по отдельности:

- `--no-mr-details` — не запрашивать детали и коммиты каждого MR (экономит ~800 запросов из ~1660);
  размер diff и число коммитов в персональных метриках станут «нет данных».
- `--no-pipeline-users` — не определять пользователя для каждого pipeline (экономит ~750 запросов
  из ~1660); связанные с пользователем поля пайплайнов станут «нет данных».
- `--light` — оба флага разом (экономит ~1200 запросов из ~1660) — то же самое, что
  `--no-mr-details --no-pipeline-users` вместе.

Полное описание — в [`SKILL.md`](./SKILL.md#cli-справочник--диспетчер-team-metrics-команда-которую-должен-запускать-агент).

## Что вы получите

Девять вкладок в одном HTML-файле:

| № | Вкладка | Источник данных | Содержимое |
|---|---|---|---|
| 01 | Обзор | Jira + GitLab | KPI целевого спринта, сводка по команде за весь период, распределение типов задач, доли успешных пайплайнов/деплоев, предупреждения |
| 02 | Спринт | только Jira | По каждому целевому спринту: бёрндаун (переключатель «Задачи»/«SP»), тепловая карта статусов, разбивка по задачам |
| 03 | Динамика команды | Jira + GitLab | Метрики спринтов Jira и 11 графиков «что менялось от спринта к спринту» (throughput, rework, MR, CI/CD, story points, …) с линией тренда |
| 04 | Прогноз | только Jira | Monte-Carlo-прогноз: перцентили P50/P85/P95, гистограмма исходов, коэффициент вариации |
| 05 | Люди — сравнение | GitLab + Jira | Сотрудники бок о бок: ключевые метрики, cycle time (среднее/медиана), полная таблица персональных метрик, персональные распределения, вклад в целевой спринт |
| 06 | Люди — динамика | GitLab + Jira | Те же персональные метрики по спринтам — многолинейные графики с трендом и карточки сотрудников с историей по всем спринтам |
| 07 | Инженерия | только GitLab | Командные пайплайны, деплои, покрытие тестами, разбивка по проектам, полнота данных GitLab |
| 08 | Данные | Jira + GitLab | Параметры запуска, экспортные таблицы (тепловая карта, доска), опись файлов папки `out/` |
| 09 | Словарь и риски | Jira + GitLab | Риски, словарь терминов, полный справочник всех метрик, роли, статусы Jira, справочник кодов предупреждений |

Вкладки 05–07 опциональны — без `GITLAB_URL`/`GITLAB_TOKEN` (или с флагом `--no-gitlab`) они
показывают себя недоступными с указанием причины, а остальные вкладки при этом строятся как обычно.

Каждый график и каждая таблица сопровождаются коротким русским пояснением: что за данные легли в
основу, как это посчитано и что означает получившееся число.

`team-metrics run` пишет все артефакты запуска в одну папку (по умолчанию `./out`, флаг
`--out-dir`): `report.json` (полные данные отчёта, схема v2) и `report.html` рядом с 18
CSV-файлами, совместимыми по именам и колонкам с набором aiIntegrationMetrics
(`gitlab_mrs.csv`, `jira_issues.csv`, `report_per_employee.csv`, `heatmap.csv`, `board.csv`, …), и
папкой `out/raw/` с необработанными данными фетчей Jira/GitLab. Полный список файлов и что в
каждом — на вкладке «08 Данные» готового отчёта.

Демо-отчёт, собранный из офлайн-фикстуры (без единого сетевого запроса), лежит в
[`demo/report-demo.html`](./demo/report-demo.html) — откройте его в браузере, чтобы увидеть все
девять вкладок сразу, включая крайние случаи (у кого-то нет статистики по диффам GitLab, один
проект пропущен, несколько метрик поделены на ноль, прогноз построился успешно).

## Установка

Все способы ниже ставят одно и то же — скилл в `~/.claude/skills/team-metrics/` (общий
каталог, который читают **и Claude Code, и opencode**, так что установка одна на оба) и команду
`team-metrics` в `~/.local/bin/`. Один и тот же скрипт [`install.sh`](./install.sh) умеет оба
режима сразу и сам определяет, какой нужен.

### Через 1 команду (рекомендуется)

```bash
curl -fsSL https://github.com/rus-lan/teamMetrics/releases/latest/download/install.sh | sh
```

Скрипт находит тег последнего релиза одним пробным запросом редиректа к
`releases/latest/download/checksums-sha256.txt` — без обращений к GitHub REST API, так что никакой
rate limit не грозит — и дальше скачивает архив с исходниками и его checksum из **этого же**
`releases/download/<тег>/` пути, чтобы они не могли прийти из двух разных релизов. Скачанный архив
сверяется с `checksums-sha256.txt`; при несовпадении установка прерывается.

Поставить конкретную версию вместо latest или сменить каталог для команды `team-metrics`:

```bash
TEAMMETRICS_VERSION=2.0.0 sh install.sh
INSTALL_DIR=/opt/bin sh install.sh
```

Проверка checksum обязательна: если в окружении нет `sha256sum`/`shasum`, скачать
`checksums-sha256.txt` не вышло или в нём нет строки для нужного файла — установка прерывается.
Обойти это (например, в минимальном окружении без sha256-утилит) можно через:

```bash
TEAMMETRICS_SKIP_CHECKSUM=1 sh install.sh
```

Настоящее несовпадение checksum (повреждённый или подменённый архив) фатально в любом случае — этот
флаг его не обходит.

### Из исходников

```bash
git clone https://github.com/rus-lan/teamMetrics.git team-metrics
cd team-metrics
./install.sh
```

`install.sh`, запущенный внутри клона репозитория, автоматически распознаёт это (по тому, что рядом
с самим скриптом лежат `SKILL.md` и `scripts/team_metrics/`) и ставит локально, без единого сетевого
запроса.

### Проверка установки

```bash
team-metrics doctor
```

Печатает по одной строке `[УСПЕШНО]`/`[ПРЕДУПРЕЖДЕНИЕ]`/`[ОШИБКА]` на каждую часть установки и
окружения (версия Python, файлы skill на месте, `team-metrics` в `PATH`, конфиг-файл, переменные
окружения) — без единого сетевого запроса и без токенов. `team-metrics --version` печатает
установленную версию.

### Удаление

```bash
./install.sh --uninstall
```

Убирает и `~/.claude/skills/team-metrics/`, и команду `team-metrics` из `~/.local/bin/`
(или `$INSTALL_DIR`, если он был задан при установке).

### Обновление с версии 1.x (проект назывался jira-metrics-report)

Начиная с 2.0.0 проект переименован: `jira-metrics-report` → `team-metrics` (подробности — в
CHANGELOG.md, раздел `[2.0.0]`). Если раньше уже ставили инструмент, обычный повторный запуск
`install.sh` сам находит и удаляет старый skill (`~/.claude/skills/jira-metrics-report/`) и старую
команду (`jira-metrics` в `~/.local/bin/` или `$INSTALL_DIR`) — печатает, что именно убрал — и ставит
новую версию рядом под новым именем. Ничего вручную удалять не нужно.

Единственное, что `install.sh` не трогает сам — файл настроек `.jira-metrics.json`, если он остался
в рабочей папке проекта: `team-metrics init`/`team-metrics doctor` укажут на него и подскажут команду
`mv .jira-metrics.json .team-metrics.json`, но не переименуют и не прочитают его автоматически.

---

Оба способа установки безопасно перезапускать сколько угодно раз — просто обновят уже установленную
копию. Работает на **Linux и macOS**. На **Windows** нативно не работает — нужен **WSL** или
**Git Bash**; внутри них `install.sh` ведёт себя точно так же, как на Linux.

Если по пути команды `team-metrics` (`~/.local/bin/team-metrics` или `$INSTALL_DIR/team-metrics`)
уже лежит чужой файл — не тот, что поставил сам `install.sh` в прошлый раз, — установка откажется
его перезаписывать и завершится с ошибкой, чтобы случайно не стереть что-то не своё. Если вы точно
хотите заменить этот файл, добавьте `--force`:

```bash
./install.sh --force
```

`Makefile` в репозитории — это необязательная обёртка для тех, кто предпочитает `make run
ARGS="..."` вместо прямого вызова: она просто вызывает то же самое `scripts/team-metrics` (или, для
установки, `install.sh`). Ничего в проекте от `make` не зависит.

Дальше — три способа **пользоваться** уже установленным инструментом; выберите раздел под свой
сценарий.

## Способ 1 — Claude Code

Клонируйте или скачайте этот репозиторий, затем из его корня:

```sh
./install.sh
```

Это установит навык в `~/.claude/skills/team-metrics/` — Claude Code подхватывает навыки из
этой папки автоматически, перезапускать сессию не нужно (если сессия уже открыта — начните новый
запрос).

Дальше просто попросите Claude Code словами — навык триггерится на фразы вроде «отчёт по метрикам
команды», «отчёт по спринту», «метрики спринта», «покажи бёрндаун», «прогноз по спринту», или на
английские «jira metrics report», «sprint report», «burndown report». Либо вызовите его явно:

```
/team-metrics
```

Дальше агент сам спросит (или возьмёт из переменных окружения, если они уже экспортированы) базовый
URL и токен Jira, имя/id нужного спринта, и при желании данные GitLab — и сам выполнит
`init`/`check`/`run` из `SKILL.md`, а в конце покажет путь к готовому `report.html`.

## Способ 2 — opencode

opencode читает те же навыки из `~/.claude/skills/` — отдельной установки не требуется, тот же
`install.sh` ставит его для обоих инструментов сразу:

```sh
./install.sh
```

Внутри opencode вызовите навык явно тем же именем:

```
/team-metrics
```

или опишите задачу естественным языком («нужен отчёт по метрикам за Sprint 42») — opencode находит
навык по тем же триггер-фразам, что и Claude Code (см. `description` в [`SKILL.md`](./SKILL.md)).
Дальнейшее поведение идентично Способу 1.

## Способ 3 — без агента, в терминале

Этот раздел самодостаточен: следуйте ему по порядку на чистой машине, ничего больше читать не нужно.

**1. Установите инструмент.**

```sh
git clone <адрес-этого-репозитория> team-metrics
cd team-metrics
./install.sh
```

В конце `install.sh` напечатает, что установлено, и (если нужно) строку для добавления в
`~/.bashrc`/`~/.zshrc`. Если он предупредил про `PATH` — добавьте строку, затем откройте новый
терминал (или выполните `source ~/.bashrc` / `source ~/.zshrc`).

**2. Создайте конфиг и задайте токены.**

```sh
cd /путь/к/вашему/проекту   # любая рабочая папка, где будет жить .team-metrics.json и report.html
team-metrics init
```

Команда напечатает:

```
файл .team-metrics.json создан
нужно ещё задать (обязательно):
  export JIRA_BASE_URL=...
  export JIRA_TOKEN=...
нужно ещё задать (необязательно — включает вкладки «Персональные»/«Инженерия»):
  export GITLAB_URL=...
  export GITLAB_TOKEN=...
отредактируйте .team-metrics.json: поле story points, проекты GitLab, список сотрудников
дальше: team-metrics check
```

Экспортируйте то, что она попросила:

```sh
export JIRA_BASE_URL="https://jira.example.com"
export JIRA_TOKEN="<ваш Jira PAT>"
export GITLAB_URL="https://gitlab.example.com"          # опционально — включает вкладки 05–07
export GITLAB_TOKEN="<ваш GitLab PAT, scope read_api>"   # опционально
```

При желании откройте `.team-metrics.json` и поправьте `gitlab.projects`, `employees`,
`story_points_field_id` под вашу команду (описание каждого ключа — в разделе
[«Конфигурационный файл»](#конфигурационный-файл--каждый-ключ) ниже). Этот шаг можно пропустить —
отчёт по вкладкам 01–04 соберётся и с конфигом по умолчанию.

**3. Проверьте, что всё подключается, прежде чем строить отчёт.**

```sh
team-metrics check --sprint-names "Sprint 42"
```

Печатает по одной строке `[УСПЕШНО]`/`[ОШИБКА]`/`[ПРОПУЩЕНО]` на каждую проверку (переменные
окружения, конфиг-файл, доступность и авторизация Jira, поле Story Points, разрешение
спринта/доски, доступность и авторизация GitLab) и завершается ненулевым кодом, если хоть одна
`[ОШИБКА]`. Это самый дешёвый способ понять, что именно сломано, ещё до попытки построить отчёт.
Например, с заглушкой вместо настоящего `JIRA_BASE_URL` и `--no-gitlab` вывод выглядит так — по
этому же виду вы поймёте, что именно чинить, и с настоящими токенами:

```
[УСПЕШНО] переменные окружения Jira — JIRA_BASE_URL=https://jira.example.invalid
[ПРОПУЩЕНО] переменные окружения GitLab — --no-gitlab
[УСПЕШНО] файл настроек — ./.team-metrics.json (или значения по умолчанию)
[ОШИБКА] подключение к Jira — jira: FieldIDs: <urlopen error [Errno -2] Name or service not known>
[ПРОПУЩЕНО] версия Jira — проверка подключения к Jira не пройдена
[ПРОПУЩЕНО] поле Story Points — проверка подключения к Jira/файла настроек не пройдена
[ОШИБКА] поиск спринта/доски — jira: SprintPicker: <urlopen error [Errno -2] Name or service not known>
[ПРОПУЩЕНО] подключение к GitLab — --no-gitlab
[ПРОПУЩЕНО] проекты GitLab — --no-gitlab
[ПРОПУЩЕНО] запрос деплоев GitLab — --no-gitlab
```

**4. Постройте отчёт.**

```sh
team-metrics run --sprint-names "Sprint 42" --history 5
```

Печатает:

```
файл с данными JSON записан: out/report.json
HTML-отчёт записан: out/report.html
```

Всё остальное (сырые данные фетчей, 18 CSV) `run` тоже пишет в ту же папку `out/` (по умолчанию;
переопределяется флагом `--out-dir`) — полный список файлов и что в каждом лежит — на вкладке
«08 Данные» готового отчёта.

Откройте `out/report.html` в любом браузере — файл полностью самодостаточен, сеть после этого шага
не нужна.

**5. Позже — перерисовать HTML без единого сетевого запроса** (если поменяли шаблон или просто
хотите пересобрать HTML из уже сохранённого `report.json`):

```sh
team-metrics report out/report.json -o report.html
```

Полный список команд и флагов — в [`SKILL.md`](./SKILL.md#cli-справочник--диспетчер-team-metrics-команда-которую-должен-запускать-агент).

## Переменные окружения (секреты — никогда не в конфиг-файле)

| Переменная | Обязательна | Как отправляется |
|---|---|---|
| `JIRA_BASE_URL` | да | — |
| `JIRA_TOKEN` | да | заголовок `Authorization: Bearer <token>` |
| `GITLAB_URL` | только чтобы включить вкладки 05–07 | — |
| `GITLAB_TOKEN` | только чтобы включить вкладки 05–07 | заголовок `PRIVATE-TOKEN: <token>`, нужен scope `read_api` |

**Токены приходят только из переменных окружения — и никогда не из конфиг-файла.** `config.py`
активно отклоняет `.team-metrics.json`, если в нём встречается ключ, похожий на секрет (`token`,
`pat`, `password`, `secret` и похожие подстроки, проверяется рекурсивно на один уровень вложенности)
— запуск падает ещё до первого сетевого запроса. Положить токен в конфиг-файл штатно нельзя.

`GITLAB_URL`/`GITLAB_TOKEN` — либо обе заданы, либо ни одной. Если задана только одна, это считается
ошибкой конфигурации и `check`/`run` завершатся с ошибкой сразу, а не после долгой попытки
подключения.

## Конфигурационный файл — каждый ключ

Опционален. Путь по умолчанию — `./.team-metrics.json`, переопределяется флагом `--config <path>`.
Готовый пример — [`.team-metrics.example.json`](./.team-metrics.example.json); JSON не поддерживает
комментарии, поэтому объяснение каждого ключа — здесь.

### Обычно нужно задать

Единственные два ключа, без которых вкладки «05»–«07» не соберутся — оба уже в бандловом
`.team-metrics.example.json`:

| Ключ | Тип | По умолчанию | Что означает |
|---|---|---|---|
| `gitlab.projects` | `[строка]` | `[]` | Пути проектов GitLab (`namespace/project`), из которых собираются данные для вкладок 05–07. Проект, который не удалось разрешить (переименован, удалён, нет доступа), попадает в `gitlab_fetch_issues.skipped_projects` — весь запуск из-за него не падает |
| `employees` | `[строка]` | `[]` | Логины GitLab, для которых собираются merge request'ы — та же строка используется для сопоставления с полем `assignee` в Jira на вкладках «05»/«06», так что в списке должен быть общий логин человека в GitLab и Jira |

`.team-metrics.example.json` также показывает `out_dir` и `status_labels` (следующая таблица) со
значениями по умолчанию — они там просто для примера формы; удалите строку или оставьте значение
по умолчанию, если менять нечего.

### Остальные ключи — нужны не всем, работают по умолчанию без конфигурации

`story_points_field_id`/`jira.final_statuses`/`status_map`/`cancelled_statuses`/`history_sprint_count`
не входят в бандловый пример (начиная с 2.0.0, см. CHANGELOG.md), но по-прежнему поддерживаются:
допишите любой из них в `.team-metrics.json` вручную, если понадобится. `out_dir`/`status_labels` —
в примере уже есть (см. выше), но тоже нужны не всем.

| Ключ | Тип | По умолчанию | Что означает | Когда реально нужен |
|---|---|---|---|---|
| `story_points_field_id` | `строка` | `""` (автоопределение по имени поля) | Id кастомного поля Jira для Story Points (например, `"customfield_10016"`) | Когда автоопределение по имени поля находит не то поле или не находит вообще — например, локализованная Jira, где поле называется не «Story Points», а на другом языке, или на инстансе несколько полей с похожим именем |
| `jira.final_statuses` | `[строка]` | `["To Test", "Ready for Initial Test", "Done", "Closed", "Ready to Deploy"]` | Именованные статусы Jira, которые **вкладки «05»/«06» (Люди)** (и только они) считают «сделано» — первое попадание в один из них закрывает задачу для этих вкладок. Вкладки «02»/«03» (Спринт/Динамика команды) этот список не используют — они опираются на собственную категорию `done` Jira (см. «Что означают метрики» ниже) | Когда у команды свой workflow с другими именами финальных статусов (например, нет «To Test»/«Ready to Deploy», а есть «QA»/«Released») — иначе вкладки «05»/«06» будут считать задачи незавершёнными дольше, чем на самом деле |
| `status_map` | `{имя статуса: категория}` | `{}` | Переопределяет, к какой *категории* статуса (`new` \| `indeterminate` \| `done` \| `cancelled`) относится «сырое» имя статуса Jira. Поиск без учёта регистра. Приоритет: `cancelled_statuses` > `status_map` > собственный каталог Jira `/rest/api/2/status` > статус не сопоставлен (в хитмапе — отдельный цвет и код `WARN_STATUS_UNMAPPED`) | Когда в собственном каталоге статусов Jira статус относится не к той категории, что нужна для отчёта (редко — обычно каталог Jira уже верный) |
| `cancelled_statuses` | `[строка]` | `["Cancelled", "Отменено", "Rejected"]` | Имена статусов, которые считаются категорией `cancelled` — имеют приоритет над `status_map` и каталогом Jira | Когда у команды есть свои имена статуса отмены задачи, не входящие в список по умолчанию (например, «Won't Fix», «Не будет сделано») |
| `history_sprint_count` | `int` | `0` → превращается в `5`, максимум `20` | Сколько предыдущих **закрытых** спринтов (кроме целевых) попадает в базовые спринты — метрики спринтов и тренд velocity на вкладке «03 Динамика команды». Переопределяется флагом `--history`, если он не ноль | Когда нужна более длинная или короткая история по умолчанию без передачи `--history` каждый раз — иначе флаг `--history` делает то же самое разово |
| `out_dir` | `строка` | `""` → превращается в `"out"` | Папка, куда `run` пишет весь результат (`report.json`, `report.html`, 18 CSV, `raw/`). Переопределяется флагом `--out-dir`, если он задан | Когда отчёты одного проекта всегда должны идти не в `./out`, а в другое место (например, отдельная папка под каждый спринт), и не хочется каждый раз передавать `--out-dir` |
| `status_labels` | `{имя статуса: русский текст}` | `{}` | Добавляет русское пояснение рядом с оригинальным именем статуса Jira (в скобках) — на хитмапе, во вкладке «09 Словарь и риски» и везде, где показан статус. Никогда не заменяет оригинальное имя, только дополняет | Когда статусы Jira называются непонятно для читателя отчёта (например, `"In Progress": "В разработке"`) |

## Что означают метрики

Полные формулы, пороги и правила для крайних случаев живут в коде — в docstring'ах и комментариях
модулей, которые ставятся вместе с инструментом (см. `<skill-dir>/scripts/team_metrics/`), а не
дублируются здесь, чтобы не разъезжаться с кодом:

- **Метрики спринта (вкладки «01 Обзор», «02 Спринт», «03 Динамика команды», «04 Прогноз»)** —
  committed/delivered/scope-change по SP и по числу задач, velocity, SMA5, load %, closure %,
  правила категорий для хитмапа, модель бёрндауна, Monte-Carlo-прогноз (бутстрап по календарному
  дневному throughput, перцентили методом nearest-rank): `metrics.py`, `burndown.py`, `forecast.py`.
- **Персональные и инженерные метрики (вкладки «05»–«07»)** — доля смёрженных MR, cycle time,
  размер диффа, доля дефектов, rework, story points, разбивка по спринтам, командные показатели по
  пайплайнам/деплоям/покрытию: `personal_metrics.py`, `engineering_metrics.py`.
- **Пороги статуса плиток и правила риска** — где именно проведена граница «норма» / «под
  наблюдением», четыре разных состояния «пустого» значения (плашка `DIV0` vs «нет данных» vs
  пустая выборка vs `null` по контракту): раздел «Статус плиток KPI» чуть ниже плюс `report_data.py`
  (`_build_board_kpi`/`_build_risks`) — единственное место, где эти пороги на самом деле заданы.

### Статус плиток KPI — считается в слое данных, не во вёрстке

С версии 3.0.0 цвет статуса плитки (`board_kpi.tiles[].status`, `good`/`warn`/`none`) — часть
самого `report.json`, посчитанная в `report_data.py`, а не решение, придуманное при вёрстке HTML.
Реальных порогов всего два — оба применяются к плиткам ТОЛЬКО целевого спринта:

- **Performance (Say/Do)** — `good`, если `performance_pct` ≥ 80, иначе `warn`.
- **Загрузка** — `good`, если `load_pct` в диапазоне 80–100 включительно, иначе `warn`.

Все остальные плитки (Commitment, Изменение объёма, Velocity SMA5, средний throughput, оба % закрытия)
всегда несут статус `none` — под них порог не определён, `render_html.py` показывает нейтральный
цвет. Третьей ступени («критично») не существует — только `good`/`warn`/`none`. Отдельно, но
похожим образом:

- **доступность прогноза**: Monte-Carlo-прогноз строится только если в истории набралось **≥ 10
  ненулевых дней throughput** (иначе `forecast.error` = `ERR_FORECAST_NOT_ENOUGH_DATA`, панель
  прогноза на вкладке «04 Прогноз» показывает «недоступно» с этой причиной, но остальной отчёт
  строится как обычно);
- **предупреждение о нестабильности**: если коэффициент вариации недельного throughput
  превышает **50%**, добавляется `WARN_THROUGHPUT_UNSTABLE` и текст `cv_warning_ru`.

Отдельно от статуса плиток вкладка «09 Словарь и риски» выводит до 4 текстовых предупреждений
(`risks[]`) по своим собственным порогам, посчитанным один раз по всей команде: успешных пайплайнов
< 80% при быстром cycle time; `defect_rate_pct` > 20; командный `rework_rate_pct` > 30; покрытие
`coverage_avg_pct` < 60. Хотите свои пороги — меняйте их в `report_data.py`
(`_build_board_kpi`/`_build_risks`), не в `render_html.py`: рендер только показывает то, что уже
посчитано и положено в JSON.

## Почему цифры на разных вкладках могут не совпадать

Вкладки «02 Спринт»/«03 Динамика команды» приходят из движка спринт-метрик Jira. Вкладки
«05 Люди — сравнение»/«06 Люди — динамика»/«07 Инженерия» — из GitLab, дополненного тем же самым
проходом по Jira, который уже сделали вкладки спринта (второго обращения к Jira нет). Обе группы
вкладок отвечают на похожие вопросы («сколько задач мы закрыли?»), но **по-разному их определяют**
— если сравнивать голые цифры между вкладками не зная этого, легко решить, что отчёт сам себе
противоречит. Инструмент сам печатает точные различия пользователю как `semantics_notes` (русский
текст) в JSON-отчёте и на вкладке «01 Обзор» — а вот почему они возникают:

1. **Привязка к спринту.** Вкладка «02 Спринт» относит задачу к спринту по *интервалам членства* в
   поле Sprint (задача может входить и выходить из спринта несколько раз — Jira хранит это в
   changelog). Вкладки «05»/«06»/«07» относят задачу к спринту по тому, попадает ли её
   *дата завершения* в календарные даты этого спринта. Одна и та же задача может законно попасть в
   разные спринты по этим двум правилам.
2. **Что считается «сделано».** Вкладка «02 Спринт» считает задачу выполненной, если к концу спринта
   её статус относится к категории `done` в самой Jira (за вычетом `cancelled_statuses`). Вкладки
   «05»/«06» считают задачу сделанной в момент *первого* попадания в один из *именованных*
   финальных статусов из `jira.final_statuses` — по умолчанию туда входят и предрелизные статусы
   вроде «To Test» и «Ready to Deploy», которые ещё не обязательно относятся к категории `done`.
   Числа с этих вкладок не сходятся один в один, и сравнивать их напрямую нельзя.
3. **День throughput.** Вкладка «02 Спринт» использует дату *последнего* перехода в статус категории
   `done` внутри спринта (переоткрытая и затем повторно исправленная задача считается один раз, по
   финальному исправлению). Вкладки «05»/«06» используют дату *первого* перехода в финальный
   статус. На переоткрытой задаче эти две даты могут разойтись на недели.
4. **Story points.** Вкладка «02 Спринт» проигрывает историю изменений поля Story Points и берёт
   значение на момент, когда задача *покинула* спринт. Вкладки «05»/«06» берут *текущее*
   значение поля на момент сбора данных. Переоценка задачи уже после закрытия спринта сдвигает сумму
   SP на вкладках «05»/«06», но никогда — на вкладке «02 Спринт»; из-за одного этого суммы SP по
   одному и тому же набору задач могут не совпасть даже на двух вкладках одного отчёта.
5. **Период.** Начиная с 3.0.0 персональная и инженерная статистика (вкладки «05»–«07») покрывает
   все анализируемые спринты (базовые + целевые), а не только целевые — суммарные числа по людям и
   CI/CD поэтому шире, чем метрики одного целевого спринта на вкладке «02 Спринт».

## Устранение неполадок

- **`team-metrics: command not found`.** `~/.local/bin` не в `PATH` — `install.sh` печатает точную
  строку `export PATH="$HOME/.local/bin:$PATH"` для вашего `~/.bashrc`/`~/.zshrc` в конце установки;
  добавьте её и откройте новый терминал. Быстрая проверка без правки rc-файла:
  `export PATH="$HOME/.local/bin:$PATH"` в текущей сессии.
- **Токен недействителен.** Невалидный или отозванный токен Jira/GitLab — это `[ОШИБКА]` в
  `team-metrics check` с кодом вроде `ERR_JIRA_AUTH_FAILED` (Jira) или `AUTH_FAILED` (GitLab).
  Отозванный **GitLab**-токен намеренно валит **весь** запуск `run` с ненулевым кодом выхода и
  `error: ...` в stderr — а не тихо превращается в пустые вкладки «05»–«07»:
  отозванный токен не должен выглядеть как чистый нулевой отчёт. Пересоздайте токен и повторите.
- **Спринт не найден.** `team-metrics check --sprint-names "..."` или `run` падает с
  `sprint not found: '...'` — проверьте точное имя спринта в Jira (сравнение без учёта регистра, но
  без опечаток) или используйте `--sprint-ids` вместо `--sprint-names`, если знаете id.
- **Проект GitLab переименован или удалён.** Это не фатальная ошибка — такой проект попадает в
  `gitlab_fetch_issues.skipped_projects` (путь проекта + код ошибки + сообщение), отображается в
  подвале готового отчёта, а остальные настроенные проекты обрабатываются как обычно. Поправьте путь
  в `gitlab.projects` в `.team-metrics.json`, когда будет удобно.
- **Прогноза нет — «недостаточно истории».** Monte-Carlo-прогноз требует **≥ 10 ненулевых дней**
  throughput за последние (до 5) закрытых спринтов, либо активного спринта, из которого можно взять
  `--target-items`. Если условие не выполняется — `forecast_error` объясняет причину, панель
  прогноза на вкладке «04 Прогноз» показывает «недоступно», а весь остальной отчёт строится как обычно
  (это не сбой). Добавьте историю (больше закрытых спринтов) или передайте `--target-items` вручную.
- **`team-metrics run`/`check` вообще не запускается.** Сначала `team-metrics check` — это
  дешёвый способ понять, что именно сломано (переменные окружения, конфиг-файл, доступность Jira,
  версия и тип развёртывания Jira, поле Story Points, разрешение спринта/доски, доступность
  GitLab), не дожидаясь, пока на этом же месте упадёт полноценный `run`.
- **`check` предупреждает про несовместимую Jira заранее.** Пункт «версия Jira» —
  `[ПРЕДУПРЕЖДЕНИЕ]`, никогда `[ОШИБКА]` (сам факт, что версию не удалось прочитать, — не повод
  блокировать иначе рабочий запуск): предупреждает, если Jira — Cloud (инструмент рассчитан на
  Server/Data Center — другая авторизация, частично другой API), и если версия ниже 8.14, где ещё
  не было Personal Access Token с заголовком `Authorization: Bearer`, которым авторизуется этот
  инструмент.
- **Деление на ноль не роняет отчёт и никогда не показывает `NaN`.** Любое отношение в отчёте (KPI в
  процентах, личные показатели MR/задач, инженерные success rate) при нулевом знаменателе
  показывается как буквальный `0` с плашкой `DIV0` и кодом `WARN_DIVISION_BY_ZERO:<метрика>` — это
  осознанно отличается от трёх других состояний пустого значения (источник вообще не вернул
  статистику, среднее/медиана по действительно пустой выборке, значение `null` по контракту) — сам
  отчёт печатает легенду всех четырёх состояний на вкладке «09 Словарь и риски».

## Устройство CLI

Есть два уровня, оба описаны в `SKILL.md`:

- [диспетчер `team-metrics`](./SKILL.md#cli-справочник--диспетчер-team-metrics-команда-которую-должен-запускать-агент) —
  `init`/`check`/`run`/`report`/`doctor`, тот же набор команд, что и в разделе «Способ 3» выше.
- [флаги `report_data.py`/`render_html.py` напрямую](./SKILL.md#cli-справочник--report_datapy-настоящая-поверхность-читайте-configpy-прежде-чем-придумывать-флаг) —
  полная, выверенная по коду таблица флагов (`--sprint-ids`/`--sprint-names`, `--board-id`,
  `--history`, `--seed`, `--target-items`, `--iterations`, `--config`, `--out-dir`, `--verbose`,
  `--quiet`, `--no-gitlab`, `--no-personal`, `--no-mr-details`, `--no-pipeline-users`, `--json`,
  `--out`, плюс `report_json`/`-o`/`--template` у `render_html.py`) — такой же набор, что и у `run`,
  кроме `run`'s собственных `--no-proxy`/`--light` и собственных `--out`/`--json-out` (HTML + JSON,
  а не только JSON).

Прямой вызов двух движков (без диспетчера `team-metrics`) тоже работает — `python3
scripts/team_metrics/report_data.py` / `render_html.py`; см. раздел «Прямой вызов скриптов» в
`SKILL.md`, если нужно разделить шаги «получить JSON» и «отрисовать HTML».
