# Changelog

Все заметные изменения проекта фиксируются в этом файле. Формат основан на
[Keep a Changelog](https://keepachangelog.com/ru/1.0.0/).

## [3.0.0] - 2026-08-07

### Изменено (ломающие изменения)

- **Схема данных v1 → v2.** `report.json` перестроен полностью: плоская структура вместо вложенного
  `payload`, проценты везде 0..100 (`_pct`), предупреждения — всегда объекты `{code, message_ru,
  detail}`, а не голые строки-коды, единая ось спринтов `sprint_axis` для всех разрезов по
  спринтам. `metrics.SCHEMA_VERSION = 2`; `team-metrics report` отклоняет любой JSON со старой
  схемой понятным русским сообщением («пересоздайте его командой `team-metrics run`») вместо того,
  чтобы рендерить мусор.
- **Артефакты `run` переехали в `out/`.** По умолчанию `report.json`/`report.html` и всё остальное
  теперь пишутся в `./out/` (переопределяется флагом `--out-dir` или ключом конфига `out_dir`), а
  не в текущую папку напрямую.
- **Период персональных и инженерных метрик расширен.** Вкладки «05»–«07» теперь считаются по всем
  анализируемым спринтам (базовые + целевые), а не только по целевым — суммарные числа по людям и
  CI/CD шире, чем на вкладке «02 Спринт» (см. README.md, «Почему цифры на разных вкладках могут не
  совпадать»).

### Добавлено

- **Девять вкладок вместо трёх** — новый HTML-отчёт: «01 Обзор», «02 Спринт», «03 Динамика
  команды», «04 Прогноз», «05 Люди — сравнение», «06 Люди — динамика», «07 Инженерия»,
  «08 Данные», «09 Словарь и риски». Каждый график и таблица сопровождается пояснением, откуда
  взяты данные и как посчитано значение.
- **Полный набор из 18 CSV-файлов и `raw/`** — `run` пишет в `out/` весь собранный/посчитанный
  материал (MR, пайплайны, деплои, покрытие, задачи Jira, разбивки по спринтам, сводки по
  сотрудникам и команде, экспорт доски и хитмапа) плюс сырые ответы Jira/GitLab в `out/raw/` —
  формат колонок совместим с набором aiIntegrationMetrics.
- **Прогресс-логи и управление их уровнем.** Новые флаги `--verbose` (DEBUG) и `--quiet` (только
  ошибки) у `run`; вывод идёт в stderr, stdout остаётся чистым для пайпов. По умолчанию — уровень
  INFO с короткими русскими строками о ходе выполнения.
- **Персональные метрики по каждому исполнителю целевого спринта** (`people_individual_jira`) —
  обязательство/поставка/performance/velocity/throughput на человека, посчитанные теми же
  формулами, что и командные плитки спринта.
- **Русский словарь предупреждений и меток** (`labels_ru.py`) — единый источник всех русских
  подписей, ролей, категорий статусов и текстов рисков; ключ конфига `status_labels` добавляет
  собственное русское пояснение статуса Jira, не заменяя оригинал.

### Безопасность

- **Экранирование CSV от formula injection перенесено в `out_writer.write_csv` и покрывает теперь
  все 18 CSV**, а не только `heatmap.csv`/`board.csv` — единая точка защиты вместо двух расходящихся
  между собой guard'ов.
- **`JIRA_BASE_URL`/`GITLAB_URL` с учётными данными (`user:pass@host`) больше не попадают в stdout
  `check`/`run`, в логи или в traceback.** Печатается и логируется только безопасная часть URL —
  тем же приёмом, что уже применялся к прокси. Некорректный такой URL теперь превращается в
  понятную русскую ошибку вместо необработанного traceback'а Python.
- Тело ошибки от Jira, попадающее в текст исключения (и оттуда — в stdout `check` и в `out/raw/`),
  теперь дополнительно очищается от собственного токена клиента.

### Исправлено

- **Сбой на этапе записи результата `run` (нехватка места на диске, `out/имя.csv` вдруг оказался
  папкой и т.п.) больше не оставляет в `out/` смесь файлов от старого и нового запуска.** Запись
  сырых данных и CSV теперь идёт во временную папку и переносится на место одним атомарным
  переименованием — падение на любом шаге оставляет предыдущий `out/` нетронутым.
- `--out`/`--json-out` с голым именем файла (без каталога) теперь уважают `--out-dir` вместо того,
  чтобы тихо писать файл в текущую папку.
- `run`/`report` отказываются писать отчёт сквозь symlink — понятная ошибка вместо тихой
  перезаписи цели symlink'а.
- `team-metrics report`/`init` на битом или отсутствующем JSON/встроенном примере конфига теперь
  печатают понятную русскую ошибку вместо traceback'а Python.
- `setup_logging()` больше не путает предустановленный `logging.FileHandler` с собственным
  stderr-хендлером.

## [2.2.0] - 2026-08-07

### Добавлено

- **Предупреждения о деплоях теперь видны прямо в отчёте, а не только в JSON.** Два разных
  случая, и в отчёте они размечены по-разному, потому что означают разное:
  - **Неполные данные** (`PAGINATION_LIMIT`) — сбор деплоев упёрся в предел пагинации или в
    дедлайн по времени, поэтому число деплоев, деплоев в неделю и доля успешных ЗАНИЖЕНЫ.
    Отмечено тем же заметным значком предупреждения, что отчёт уже использует для деления на
    ноль, — и на плитках вкладки «Деплои», и в строке затронутого проекта, с именами
    затронутых проектов. Это главный из двух случаев: усечённый список деплоев, который
    показывает правдоподобное, но заниженное число, — ровно то, для чего существует значок
    предупреждения.
  - **Медленный путь** (`FILTER_REJECTED_FALLBACK`) — сервер отклонил отфильтрованный запрос, и
    клиент заново запросил данные без фильтра по дате. Цифры при этом ВЕРНЫЕ, дороже обошёлся
    только сам запуск. Тихая заметка в подвале отчёта с именами затронутых проектов, прямо
    говорящая, что на цифры это не влияет.
  - Новый ключ `report["gitlab_fetch_issues"]["deployment_warnings"]` — рядом с уже
    существующими `skipped_projects`/`mr_fetch_errors`.

## [2.1.2] - 2026-08-07

### Исправлено

- **Запрос деплоев GitLab снова отклонялся живым сервером GitLab 19.0 — уже после фикса
  сортировки в 2.1.1.** На этот раз сервер потребовал ещё и фильтр по статусу: `finished_at
  filter must be combined with success status filter`.
  - Отправить `status=success` мы не можем: тот же запрос питает `deploy_success_rate_pct`, для
    которого нужны в том числе неудачные деплои — отфильтровав их, доля неудач в метрике тихо
    обнулилась бы.
  - Исправление: серверную фильтрацию по `finished_at` убрали совсем. Вместо неё отправляется
    только грубый `updated_after` без верхней границы, а точное окно применяется на своей
    стороне — по `finished_at` каждого деплоя. Верхней границы нет намеренно: GitLab
    проставляет `finished_at` в том же сохранении, что двигает `updated_at`, а все последующие
    фоновые задачи только сдвигают `updated_at` дальше вперёд — значит, открытая снизу граница
    доказуемо не может потерять деплой, завершившийся внутри окна, а любой фиксированный запас
    сверху был бы догадкой, которая могла ошибиться.
  - Если сервер отклонит с 400 даже такой урезанный запрос, клиент один раз повторяет его вовсе
    без фильтра по дате и целиком фильтрует окно на своей стороне — с предупреждением, чтобы
    было видно, что именно этот сервер вынудил инструмент на более медленный путь.
  - Сбор деплоев, упёршийся в предел пагинации или дедлайн по времени, теперь возвращает уже
    собранные частичные записи с предупреждением вместо того, чтобы обрывать весь запуск.

### Добавлено

- `fetch_team_data()` возвращает новый ключ `deployment_warnings` — рядом с уже существующими
  `skipped_projects`/`mr_fetch_errors` — со всеми предупреждениями про урезанные/повторные/
  частичные сборы деплоев из пункта выше.

## [2.1.1] - 2026-08-07

### Исправлено

- **Запрос деплоев GitLab отклонялся с HTTP 400.** `GitLabClient.deployments()` фильтровал по
  `finished_after`/`finished_before`, но не задавал сортировку — документация GitLab только
  «рекомендует» указывать `order_by=finished_at` вместе с этим фильтром, но живой сервер GitLab
  19.0 требует это жёстко: `400 Bad request - \`finished_at\` filter requires \`finished_at\`
  sort.` Документация и поведение сервера расходятся в строгости — не убирайте `order_by`/`sort`
  как «избыточные» параметры, сервер их реально требует. Отдельно: документация также предлагает
  добавить туда `status=success` — это намеренно НЕ сделано, потому что тот же запрос питает
  `deploy_success_rate_pct`, для которого нужны и неудачные деплои тоже; `status=success` тихо
  обнулил бы долю неудач в этой метрике.

### Добавлено

- Новый пункт в `check` — пробный запрос к эндпоинту деплоев GitLab («запрос деплоев GitLab»),
  тем же методом и в той же форме, что использует `run`, но для одного проекта и минимального
  окна. Раньше эта несовместимость обнаруживалась только после ~1600 запросов, когда `run` уже
  падал на середине сбора данных, — теперь `check` ловит её заранее. `[ОШИБКА]` только на HTTP
  400 (сам запрос некорректен); `[ПРЕДУПРЕЖДЕНИЕ]`, не `[ОШИБКА]`, если проблема временная или
  связана с правами на конкретный проект (403/404 и т.п.) — это не значит, что форма запроса
  неверна.

## [2.1.0] - 2026-08-07

### Добавлено

- Новый пункт в `check` — версия и тип развёртывания Jira («версия Jira»). Печатает, к какой
  именно Jira подключился инструмент (например, `Jira Server 9.12.28`), вместо того чтобы дать
  несовместимости обнаружиться позже, посреди `run`. Предупреждает (`[ПРЕДУПРЕЖДЕНИЕ]`, никогда
  `[ОШИБКА]`):
  - если это Jira Cloud — инструмент рассчитан на Server/Data Center, а у Cloud другая схема
    авторизации (email + API-токен через Basic) и частично другой API;
  - если версия ниже 8.14 — именно в этой версии появились Personal Access Token с заголовком
    `Authorization: Bearer`, которым авторизуется инструмент, — ниже авторизация работать не будет;
  - если версию определить не удалось (например, эндпоинт закрыт на конкретном инстансе) — сам по
    себе этот факт не повод блокировать иначе рабочий запуск.

## [2.0.0] - 2026-08-06

### Изменено

- **Переименование проекта: `jira-metrics-report` → `team-metrics`**, вслед за именем репозитория
  (`rus-lan/teamMetrics`):
  - Python-пакет `scripts/jira_metrics/` → `scripts/team_metrics/` (и `python3 -m jira_metrics` →
    `python3 -m team_metrics`).
  - Исполняемый скрипт `scripts/jira-metrics` → `scripts/team-metrics`.
  - Skill/каталог установки `jira-metrics-report` → `team-metrics`, теперь ставится в
    `~/.claude/skills/team-metrics/`.
  - Конфиг-файл `.jira-metrics.json` → `.team-metrics.json` (пример — `.jira-metrics.example.json`
    → `.team-metrics.example.json`).
  - Переменная окружения `JIRA_METRICS_BIN` → `TEAM_METRICS_BIN`.
  - Архив релиза `jira-metrics-report.tar.gz` → `team-metrics.tar.gz`.
  - `JIRA_BASE_URL`/`JIRA_TOKEN`/`GITLAB_URL`/`GITLAB_TOKEN` **не переименованы** — они называют
    внешние системы (Jira, GitLab), а не сам инструмент.
- **Миграция для тех, кто уже ставил 1.x**: `install.sh` при каждой установке сам находит и удаляет
  старый skill (`~/.claude/skills/jira-metrics-report/`) и старую команду `jira-metrics` в
  `INSTALL_DIR` — но только если это наш собственный лаунчер (проверяется по тому же маркеру, что и
  `--uninstall`), никогда не трогает чужой файл. `team-metrics init`/`team-metrics doctor`
  предупреждают, если в рабочей папке остался `.jira-metrics.json` без `.team-metrics.json` рядом, и
  подсказывают команду для переименования — не читают и не переименовывают его автоматически.
- Бандловый `.team-metrics.example.json` сокращён до двух ключей, которые реально нужно задать
  почти всегда — `gitlab.projects` и `employees`. `status_map`, `cancelled_statuses`,
  `story_points_field_id`, `history_sprint_count`, `jira.final_statuses` по-прежнему
  поддерживаются конфиг-загрузчиком с теми же значениями по умолчанию — задавайте их вручную, если
  понадобятся (см. README.md, раздел «Конфигурационный файл»).

### Добавлено

По итогам независимого аудита безопасности/надёжности:

- Новые флаги `--no-mr-details` и `--no-pipeline-users` (и их комбинация одним флагом `--light`) у
  `run` — отключают два самых тяжёлых обхода GitLab (детали+коммиты каждого MR, пользователь
  каждого pipeline) по отдельности или разом, экономя до ~1200 запросов из ~1660 в среднем `run`.
  `--no-mr-details`/`--no-pipeline-users` доступны и у `report_data.py` напрямую.
- Новый флаг `--no-proxy` у `check`/`run` — игнорирует `HTTP_PROXY`/`HTTPS_PROXY` из окружения для
  запросов и к Jira, и к GitLab.
- `run`/`report_data.py` считает и печатает число фактических HTTP-запросов к GitLab
  (`gitlab_request_count`) в конце `run`.

### Исправлено

По итогам того же аудита:

- GitLab-клиент уважает заголовок `Retry-After` от сервера при 429/5xx (с потолком
  `max_retry_after`) вместо фиксированной экспоненциальной задержки между ретраями.
- `install.sh` отказывается перезаписать чужой файл на месте команды `team-metrics`
  (бывш. `jira-metrics`) без явного `--force`, чтобы случайно не стереть что-то не своё.
- Форматирование дат в отчёте починено под Python 3.9 (нуль в начале года).

## [1.0.0] - 2026-08-06

Первый публичный релиз. Инструмент готов к использованию: 517 тестов,
без сторонних зависимостей — чистый stdlib Python 3.9+.

### Добавлено

- Единая командная поверхность `jira-metrics {init|check|run|report|doctor}` —
  без `pip install`, работает как исполняемый скрипт из репозитория или как
  установленная команда после `install.sh`.
- Вкладка «Команда»: KPI спринта (committed/delivered/scope-change по story
  points и по числу задач), velocity и SMA5, load %, closure %, бёрндаун,
  хитмап статусов, Monte-Carlo-прогноз по спринту.
- Вкладка «Персональные»: метрики каждого разработчика по GitLab (доля
  смёрженных merge request'ов, cycle time, размер диффа, rework) и по Jira
  (story points, доля дефектов, разбивка по спринтам).
- Вкладка «Инженерия»: командные показатели по пайплайнам, деплоям и
  покрытию тестами из GitLab.
- Самодостаточный HTML-отчёт — открывается в любом браузере, сеть после
  генерации не нужна.
- `jira-metrics check` — проверка подключения к Jira/GitLab и конфигурации
  без построения отчёта.
- `jira-metrics doctor` — диагностика окружения и установки skill, без
  сети и без токенов.
- `jira-metrics --version` — печатает установленную версию.
- Установка одной командой: `curl -fsSL
  https://github.com/rus-lan/teamMetrics/releases/latest/download/install.sh | sh`
  — скачивает архив последнего релиза, проверяет его sha256 и ставит.
  Тот же `install.sh`, запущенный внутри клона репозитория, ставит локально
  без сети.
