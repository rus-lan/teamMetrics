# team-metrics

Одна командная поверхность на чистом stdlib Python 3.9+, `pip install` нигде не нужен:

```sh
<skill-dir>/scripts/team-metrics {init|check|run|report|doctor} ...
```

Установка одной командой (см. README.md, раздел «Установка»):

```sh
curl -fsSL https://github.com/rus-lan/teamMetrics/releases/latest/download/install.sh | sh
```

После установки через [`install.sh`](./install.sh) (из релиза одной командой выше или локально из
клона репозитория) та же команда доступна короче, из любого каталога, как `team-metrics
{init|check|run|report|doctor} ...` — `install.sh` кладёт лаунчер в `~/.local/bin/team-metrics`,
который вызывает ровно этот же `<skill-dir>/scripts/team-metrics`. Дальше в этом файле оба
варианта равнозначны; там, где путь важен буквально, используется `<skill-dir>/scripts/team-metrics`.

Пять подкоманд покрывают весь процесс — `init` пишет конфиг-файл, `check` проверяет
доступность Jira/GitLab, ничего не строя, `run` получает данные + считает метрики + пишет и JSON,
и HTML, `report` перерисовывает HTML из уже полученного JSON-файла **без единого** сетевого
запроса, `doctor` проверяет окружение и саму установку skill (без сети, без токенов — можно
запускать сразу после установки). Точную последовательность команд смотрите в разделе «Порядок
вызова» ниже.

Под капотом это диспетчер поверх тех же двух движков, что и раньше (их по-прежнему можно вызывать
напрямую — см. «Прямой вызов скриптов» ниже):

1. **`report_data.py`** — получает данные из Jira (и опционально GitLab), считает все метрики и
   отдаёт один JSON-сериализуемый словарь (`build_combined_report()`).
2. **`render_html.py`** — читает этот словарь и подставляет его в `templates/report.html`,
   получая один самодостаточный файл `.html`: без `<script src>`, без внешних `<link>`, без
   `@import`, без единого сетевого запроса во время просмотра. Открывается через `file://` вечно,
   офлайн.

Этот файл описывает, что нужно модели, чтобы правильно запустить инструмент. Полная схема
JSON-конфига, определения метрик и откуда берутся цифры — в [`README.md`](./README.md)
(`<skill-dir>/README.md`, после установки — `~/.claude/skills/team-metrics/README.md`).

## Требования

- Python 3.9+, только стандартная библиотека. Никаких сторонних пакетов, сеть для *просмотра*
  готового отчёта не нужна (только для его *генерации*, и только в сторону Jira/GitLab).
- `JIRA_BASE_URL` и `JIRA_TOKEN` в окружении — **обязательно**.
- `GITLAB_URL` и `GITLAB_TOKEN` в окружении — **опционально**; без них вкладки «05»–«07» сообщают
  о себе `"available": false` с причиной, остальные вкладки при этом строятся как обычно.

Прежде чем запускать `run` против настоящих боевых Jira/GitLab (не демо, не тестового стенда),
предупредите пользователя о разделах README.md
[«Прежде чем указывать инструмент на прод»](./README.md#прежде-чем-указывать-инструмент-на-прод)
и [«Объём запросов»](./README.md#объём-запросов--не-указывайте-на-прод-вслепую) — коротко: PAT в
Jira Server/DC нельзя выпустить read-only (утечка токена = полный доступ аккаунта), прокси в
окружении видит `Authorization: Bearer <token>`, и полный `run` — это ~12 запросов к Jira, но до
~1660–6600 к GitLab. Для первого прогона на новом проекте предлагайте `--no-gitlab`, затем
`--no-personal`, и только потом полный `run` — как описано там же.

  что означает каждый ключ — в README.md (в JSON нет комментариев)
- `<skill-dir>/VERSION` — текущая версия инструмента, единственный источник правды (см.

  без задач, пропущенный проект GitLab, несколько метрик с делением на ноль. Откройте его, чтобы
  увидеть форму реального вывода до первого запуска против настоящих Jira/GitLab. Присутствует при
  локальной установке из клона репозитория; в минимальном архиве релиза, который ставится одной
  командой (`curl | sh`), его нет — инструменту он в рантайме не нужен, это просто пример для
  человека.
- `<skill-dir>/install.sh` — устанавливает/переустанавливает этот каталог в
  `~/.claude/skills/team-metrics/` и кладёт команду `team-metrics` в `~/.local/bin/`; см.
  README.md, раздел «Установка».

## Порядок вызова

Запускайте `<skill-dir>/scripts/team-metrics` (или просто `team-metrics`, если установлено через
`install.sh`) из каталога, где должен жить `.team-metrics.json` (рабочая папка конкретного проекта,
а не сам `<skill-dir>`) — либо передавайте `--config` явно в `check`/`run`. Два сценария, две
короткие последовательности:

**Первая настройка для проекта** (`.team-metrics.json` ещё нет):

```sh
team-metrics init
# -> пишет ./.team-metrics.json, печатает, каких переменных окружения не хватает

export JIRA_BASE_URL="https://jira.example.com"
export JIRA_TOKEN="<PAT из Jira>"
export GITLAB_URL="https://gitlab.example.com"    # опционально — включает вкладки 05–07
export GITLAB_TOKEN="<PAT из GitLab>"              # опционально

# при необходимости отредактируйте ./.team-metrics.json: gitlab.projects, employees, story_points_field_id

team-metrics check --sprint-names "Sprint 42"
# -> построчно [УСПЕШНО]/[ОШИБКА]/[ПРОПУЩЕНО] по каждому пункту: переменные окружения, доступность/авторизация Jira/GitLab, поле Story Points, разрешение спринта/доски

team-metrics run --sprint-names "Sprint 42" --history 5
# -> пишет out/report.json, out/report.html, 18 CSV в out/, сырые данные фетчей в out/raw/
# (папка вывода переопределяется флагом --out-dir, по умолчанию "out")
```

**Перерисовка** уже полученного `report.json` (без сети, можно отредактировать JSON или просто
переоформить):

```sh
team-metrics report report.json -o report.html
```

`init`/`check` — разовые или периодические (перезапускайте `check`, когда могли поменяться
учётные данные); `run` — обычная повседневная команда после того, как настройка сделана. И `run`,
и `report` также работают через пайп/stdin, как и прямые скрипты — см. «Прямой вызов скриптов»
ниже, если нужно разделить два движка (например, чтобы посмотреть/поправить JSON между получением
данных и рендером, чего `run` не даёт — используйте `--json-out` у `run` плюс отдельный вызов
`report`).

## CLI-справочник — диспетчер `team-metrics` (команда, которую должен запускать агент)

| Команда | Что делает | Ключевые флаги |
|---|---|---|
| `init [--force]` | Пишет `.team-metrics.json` в текущем каталоге из встроенного примера. Отказывается перезаписать существующий файл без `--force`. Никогда не пишет токен. Печатает, каких переменных окружения не хватает, и следующую команду | `--force` |
| `check [--sprint-ids/--sprint-names] [--board-id] [--config] [--no-gitlab] [--no-proxy]` | Проверяет настройку **без построения отчёта**: переменные окружения, конфиг-файл, доступность+авторизация Jira, версия и тип развёртывания Jira, обнаружение поля Story Points, разрешение спринта/доски (только если задано), доступность+авторизация GitLab и — если настроен `gitlab.projects` — что каждый настроенный проект действительно разрешается. Печатает по одной строке `[УСПЕШНО]`/`[ОШИБКА]`/`[ПРОПУЩЕНО]`/`[ПРЕДУПРЕЖДЕНИЕ]` на пункт, токен никогда не печатает; завершается ненулевым кодом при любом `[ОШИБКА]` | те же целевые флаги, что у `run`, здесь все опциональны, плюс `--no-proxy` |
| `run <target> [flags] [--out <html>] [--json-out <json>]` | Полный цикл: получить → посчитать → записать **и** JSON-файл данных, **и** HTML-отчёт. Здесь работает каждый флаг `report_data.py` из таблицы ниже, плюс три флага только диспетчера ниже. В конце печатает число фактических HTTP-запросов к GitLab за этот запуск (`gitlab_request_count`) | `--out` (по умолчанию `<out-dir>/report.html`), `--json-out` (по умолчанию `<out-dir>/report.json`), `--no-proxy`, `--no-mr-details`, `--no-pipeline-users`, `--light` |
| `report [json_path] [-o <html>] [--template <path>]` | Рендерит HTML из существующего JSON-файла данных — **ноль** сетевых запросов, вообще не читает `JIRA_*`/`GITLAB_*`. Отклоняет JSON-файл с незнакомым `schema_version` с понятной ошибкой вместо рендера мусора | `-o/--out` (по умолчанию stdout), `--template` |
| `doctor` | Проверяет окружение и установку skill — версия Python, файлы skill на месте, `team-metrics` в `PATH`, конфиг-файл, переменные окружения, самопроверка шаблона отчёта, прокси. Без сети, без токенов — можно запускать сразу после установки | нет |

Флаги target/history/seed и т.д. у `run` идентичны флагам `report_data.py` (см. таблицу чуть
ниже) — `run` строго надмножество, а не другой набор флагов, за исключением того, что его `--out`
означает путь к **HTML**, а `--json-out` — новый флаг для пути к JSON (собственный `--out` у
`report_data.py`, при прямом вызове, как и раньше означает путь к JSON, без изменений).

`check`/`run` также принимают флаги, которых нет в общей таблице `report_data.py` ниже (кроме
`--no-mr-details`/`--no-pipeline-users`, которые есть и там):

| Флаг | Где доступен | Значение |
|---|---|---|
| `--no-proxy` | `check`, `run` | Игнорировать `HTTP_PROXY`/`HTTPS_PROXY` из окружения для запросов и к Jira, и к GitLab — подключаться напрямую, не трогая сами переменные окружения процесса |
| `--no-mr-details` | `run`, `report_data.py` | Не запрашивать детали и коммиты каждого MR — экономит ~800 запросов к GitLab из ~1660 в среднем `run`; размер diff и число коммитов в персональных метриках станут «нет данных» |
| `--no-pipeline-users` | `run`, `report_data.py` | Не определять пользователя для каждого pipeline — экономит ~750 запросов к GitLab из ~1660 в среднем `run`; связанные с пользователем поля пайплайнов станут «нет данных» |
| `--light` | `run` (только у диспетчера — комбинирует два флага выше) | Отключить оба тяжёлых обхода GitLab разом (то же самое, что `--no-mr-details --no-pipeline-users` вместе) — экономит около 1200 запросов из ~1660 в среднем `run` |

`--no-mr-details`/`--no-pipeline-users` нет у `check` — `check` не обходит MR/pipeline'ы по одному,
эти флаги там были бы бессмысленны.

## Прямой вызов скриптов (продвинутый/низкоуровневый вариант — те же два движка, что оборачивают `run`/`report`)

**Здесь `--out` означает не то же самое, что у `team-metrics run`.** Ниже `report_data.py --out`
пишет **JSON**-файл данных (у этого скрипта вообще нет HTML-вывода — это работа `render_html.py`,
через его собственный отдельный `-o/--out`). У диспетчера `run --out` пишет **HTML**-отчёт, а
`--json-out` — это путь к JSON. Если привыкли к одной форме — проверяйте, какой именно `--out`
держите в руках, прежде чем запускать: не тот `--out` тихо перезапишет не тот файл.

Двухшаговый конвейер, запускать из каталога, откуда должен резолвиться `.team-metrics.json` (или
передавайте `--config` явно):

```sh
JIRA_BASE_URL="https://jira.example.com" JIRA_TOKEN="<PAT>" \
GITLAB_URL="https://gitlab.example.com" GITLAB_TOKEN="<PAT>" \
python3 <skill-dir>/scripts/team_metrics/report_data.py \
  --sprint-ids 4821 --history 5 --out /tmp/report.json   # <- путь к JSON, собственный --out report_data.py

python3 <skill-dir>/scripts/team_metrics/render_html.py /tmp/report.json -o report.html
```

Либо одним пайпом (`report_data.py --json` печатает в stdout; `render_html.py` по умолчанию
читает stdin):

```sh
JIRA_BASE_URL=... JIRA_TOKEN=... python3 <skill-dir>/scripts/team_metrics/report_data.py \
  --sprint-names "Sprint 42" --json | python3 <skill-dir>/scripts/team_metrics/render_html.py -o report.html
```

## CLI-справочник — `report_data.py` (настоящая поверхность; читайте `config.py`, прежде чем придумывать флаг)

Целевой спринт, **взаимоисключающе, ровно один обязателен**:

| Флаг | Значение |
|---|---|
| `--sprint-ids <id[,id...]>` | Id спринтов Jira через запятую (целевые спринты) |
| `--sprint-names <name[,name...]>` | Имена спринтов через запятую. Точное совпадение, без учёта регистра, с обрезкой пробелов; при совпадении двух имён побеждает спринт с меньшим id |

Всё остальное опционально:

| Флаг | По умолчанию | Значение |
|---|---|---|
| `--board-id <int>` | нет | Сверяется с доской, к которой относятся разрешённые целевые спринты; несовпадение — жёсткая ошибка, а не тихая подмена |
| `--history <int>` | `0` → 5, максимум 20 | Сколько предыдущих **закрытых** спринтов анализируется в дополнение к целевым — заполняет board_table/тренд velocity и ЭТА ЖЕ ось спринтов служит выборкой для Monte-Carlo-прогноза (`04 Прогноз`); мало истории — командного прогноза может не быть («недостаточно данных», см. «Диагностика» ниже), поднимите `--history` |
| `--seed <int>` | `42` | Seed для RNG бутстрапа Monte-Carlo — тот же seed, тот же запуск, те же числа прогноза |
| `--iterations <int>` | `0` → 5000 | Число итераций Monte-Carlo |
| `--config <path>` | `./.team-metrics.json`, если существует | Путь к JSON-конфигу |
| `--json` | выкл | Напечатать полный словарь отчёта как JSON в stdout |
| `--out <path>` | нет | Записать JSON-отчёт в этот файл |
| `--no-gitlab` | выкл | Пропустить **все** вкладки на GitLab (05–07), даже если `GITLAB_URL`/`GITLAB_TOKEN` заданы |
| `--no-personal` | выкл | Пропустить только вкладки персональных метрик («05»/«06»); вкладка «07 Инженерия» (командный уровень, не по людям) всё равно строится, пока настроен GitLab |
| `--no-mr-details` | выкл | Не запрашивать детали и коммиты каждого MR — экономит ~800 запросов к GitLab из ~1660 в среднем `run`; размер diff и число коммитов в персональных метриках станут «нет данных» |
| `--no-pipeline-users` | выкл | Не определять пользователя для каждого pipeline — экономит ~750 запросов к GitLab из ~1660 в среднем `run`; связанные с пользователем поля пайплайнов станут «нет данных» |
| `--out-dir <path>` | `./out` | Папка для собранных данных и отчётов (тот же флаг, что и у `run`) |
| `--verbose` | выкл | Подробные логи (уровень DEBUG) в stderr |
| `--quiet` | выкл | Только ошибки (уровень ERROR) в stderr |

`report_data.py` не принимает `--no-proxy`/`--light` напрямую — оба существуют только на уровне
диспетчера `team-metrics` (`check`/`run`), см. таблицу выше.

`render_html.py`: позиционный `report_json` (путь, по умолчанию — stdin), `-o/--out <path>`
(по умолчанию — stdout), `--template <path>` (переопределение, по умолчанию —
`templates/report.html` рядом с модулем).

## Окружение — секреты никогда не попадают в конфиг-файл

| Переменная | Обязательна | Как отправляется |
|---|---|---|
| `JIRA_BASE_URL` | да | — |
| `JIRA_TOKEN` | да | `Authorization: Bearer <token>` |
| `GITLAB_URL` | только чтобы включить вкладки 05–07 | — |
| `GITLAB_TOKEN` | только чтобы включить вкладки 05–07 | заголовок `PRIVATE-TOKEN: <token>`, нужен scope `read_api` в GitLab |

Говорите это пользователю прямо: **токены приходят только из окружения.** JSON-конфиг
(`.team-metrics.json`) активно **отклоняет** любой ключ, похожий на секрет — `token`,
`jira_token`, `gitlab_token`, `pat`, `password`, `secret`, проверяется рекурсивно на один уровень
вложенности (например, внутри `"gitlab": {...}`) — `config.py` кидает `ConfigError`, и запуск
падает ещё до сети, если такой ключ найден. Никогда не предлагайте положить токен в
`.team-metrics.json`, никогда не показывайте значение токена пользователю обратно, никогда не
пишите его в готовый HTML — токен туда не попадает вообще ни в каком виде (не «скрыт», а просто
отсутствует: `render_html.py` его не читает и никуда не подставляет).

`GITLAB_URL`/`GITLAB_TOKEN` — либо обе заданы, либо ни одной. Если задана ровно одна — это
считается ошибкой конфигурации и падает сразу, поскольку наполовину настроенное подключение к
GitLab всё равно рано или поздно с шумом сломается.

## Папка `out/` — куда попадают все артефакты запуска

`run` пишет всё в одну папку (по умолчанию `./out`, флаг `--out-dir`), в этом порядке: сырые данные
фетчей Jira/GitLab в `out/raw/`, затем 18 CSV-файлов, затем `report.json`, затем `report.html`.
Полный список файлов с расшифровкой каждого — на вкладке «08 Данные» готового отчёта. CSV-файлы
совместимы по именам с набором aiIntegrationMetrics (`gitlab_mrs.csv`, `jira_issues.csv`,
`jira_by_sprint.csv`, `gitlab_by_sprint.csv`, `report_per_employee.csv`, `report_team.csv`,
`report_merged.csv`, `heatmap.csv`, `board.csv`, …) — и по колонкам везде, кроме
`report_per_employee.csv`: с 3.1.0 в нём больше нет `deployment_count`/`deployment_failed`/
`deployment_fail_rate` (см. CHANGELOG.md). Числа в CSV остаются в конвенции источника
(доли 0..1), тогда как те же метрики в `report.json`/`report.html` — проценты 0..100. Без
`--no-gitlab` фетчится и пишется всё; с `--no-gitlab` GitLab-именованные CSV и `out/raw/gitlab_*`
отсутствуют, запуск всё равно завершается кодом 0.

## Девять вкладок и пять расхождений в терминах между ними

Вкладки «02 Спринт»/«03 Динамика команды»/«04 Прогноз» приходят только из движка спринт-метрик
Jira. Вкладки «05 Люди — сравнение»/«06 Люди — динамика»/«07 Инженерия» собираются из GitLab,
дополняя тот же самый проход по Jira, который уже сделали вкладки спринта (второго обращения к
Jira нет) плюс проход по GitLab. Поскольку они отвечают на пересекающиеся вопросы («сколько задач
мы закрыли?») **разными определениями**, читатель, который сравнивает голые числа между вкладками,
иначе решит, что отчёт сам себе противоречит. Инструмент уже печатает пользователю точные различия
как `semantics_notes` (русский текст) в JSON-отчёте и на вкладке «01 Обзор» — а здесь объясняется,
ПОЧЕМУ они возникают:

1. **Привязка к спринту.** Вкладка «02 Спринт» относит задачу к спринту по *интервалам членства* в
   поле Sprint (задача может входить и выходить из спринта несколько раз — Jira хранит это в
   changelog). Вкладки «05»–«07» относят задачу к спринту по тому, попадает ли её *дата
   завершения* в календарные даты этого спринта. Одна и та же задача может законно попасть в
   разные спринты по этим двум правилам.
2. **Определение «сделано».** Вкладка «02 Спринт» считает задачу выполненной, если к концу спринта
   её статус относится к собственной категории `done` в Jira (за вычетом `cancelled_statuses`).
   Вкладки «05»/«06» считают задачу сделанной в момент *первого* попадания в один из *именованных*
   финальных статусов из `jira.final_statuses` — по умолчанию туда входят и предрелизные статусы
   вроде «To Test» и «Ready to Deploy», не обязательно относящиеся к категории `done`. Числа с этих
   вкладок никогда не сходятся один в один, и сравнивать их напрямую нельзя.
3. **День throughput.** Вкладка «02 Спринт» использует дату *последнего* перехода в статус
   категории `done` внутри спринта (переоткрытая и затем повторно исправленная задача считается
   один раз, по финальному исправлению). Вкладки «05»/«06» используют дату *первого* перехода в
   финальный статус. На переоткрытой задаче эти две даты могут разойтись на недели.
4. **Story points.** Вкладка «02 Спринт» проигрывает историю изменений поля Story Points и берёт
   значение, которое было у поля в момент, когда задача *покинула* спринт. Вкладки «05»/«06» берут
   *текущее* значение поля на момент сбора данных. Переоценка задачи уже после закрытия спринта
   сдвигает сумму SP на вкладках «05»/«06», но никогда — на вкладке «02 Спринт»; из-за одного этого
   суммы SP могут не совпасть даже для одного и того же набора задач.
5. **Период.** С версии 3.0.0 персональная и инженерная статистика («05»–«07») покрывает все
   анализируемые спринты (базовые + целевые), а не только целевые — суммарные числа шире, чем
   метрики одного целевого спринта на вкладке «02 Спринт».

## Устранение неполадок

- **Перед `run` запускайте `check`, если токен/URL мог поменяться.** Это быстрый способ, ничего не
  строя, узнать, что именно сломано (переменные окружения, конфиг-файл, авторизация/доступность
  Jira, поле Story Points, разрешение спринта/доски, авторизация/доступность GitLab) — дешевле, чем
  дождаться, пока на этом же месте упадёт полноценный `run`.
- **`check` называет, к какой именно Jira подключился, и предупреждает заранее, а не после
  падения на середине `run`.** Пункт «версия Jira» — `[ПРЕДУПРЕЖДЕНИЕ]`, никогда `[ОШИБКА]`, если
  версию узнать не удалось (эндпоинт `/rest/api/2/serverInfo` на некоторых инстансах закрыт) — сама
  по себе это не причина блокировать запуск, который иначе бы отработал. Отдельно предупреждает,
  если `deploymentType` — Cloud (инструмент рассчитан на Server/Data Center: другая схема
  авторизации и частично другой API), и если версия ниже 8.14 (Personal Access Token с заголовком
  `Authorization: Bearer`, которым авторизуется этот инструмент, появились именно в 8.14.0 — ниже
  авторизация физически не сможет работать).
- **Отозванный или недействительный токен GitLab валит весь запуск с шумом — так и задумано.**
  `AUTH_FAILED` намеренно всплывает из `fetch_team_data()` вместо того, чтобы тихо превратиться в
  пустой раздел персональных/инженерных метрик — отозванный токен не должен выглядеть как чистый,
  нулевой отчёт. Ненулевой код выхода, `error: ...` в stderr.
- **Один недоступный или переименованный проект GitLab — не фатальная ошибка.** Он попадает в
  `gitlab_fetch_issues.skipped_projects` (путь проекта + код ошибки + сообщение) и отображается в
  подвале готового отчёта; все остальные настроенные проекты всё равно обрабатываются.
- **Прогноз может деградировать по частям, не обрушивая отчёт.** С версии 3.1.0 прогноз считается
  дважды независимо — по команде и по каждому человеку — из фактически поставленных Story Points за
  закрытые спринты оси (`sprints[].metrics.delivered_sp`), а не по дневному throughput в днях, как
  раньше. `forecast.available` относится только к командному прогнозу: меньше 3 закрытых спринтов
  на оси — `forecast.team` = `null`, `forecast.error` = `{code: "ERR_FORECAST_NOT_ENOUGH_DATA", ...}`,
  панель «04 Прогноз» показывает причину вместо командных цифр. Персональный прогноз для каждого
  человека требует отдельно **минимум 2** закрытых спринтов со Story Points — недостаточная история
  даёт `forecast.people[].available = false` с `unavailable_reason_ru`, но не трогает ни командный
  прогноз, ни прогнозы остальных людей. Оба случая штатные, не сбой.
- **Будущий/активный спринт без `startDate`/`endDate` всё равно рендерится.** Бёрндаун показывает
  «нет данных» (0 календарных дней) вместо падения; хитмап и строки доски для этого спринта не
  затронуты.
- **Деление на ноль никогда не роняет отчёт и никогда не показывает `NaN`.** Любое отношение в этом
  инструменте (проценты KPI, личные показатели MR/задач, success rate инженерии) при нулевом
  знаменателе показывается по контракту «0 + предупреждение»: ноль-знаменатель рендерится как
  буквальный `0` с плашкой `DIV0` и кодом `WARN_DIVISION_BY_ZERO:<metric>` — это намеренно отличается
  от трёх других состояний пустого значения (источник вообще не вернул статистику, среднее/медиана
  по действительно пустой выборке, значение `null` по контракту) — точные правила рендера и
  легенда из четырёх состояний печатает сам отчёт (вкладка «09 Словарь и риски»), обзор — в
  README.md.
- **Ноль сторонних зависимостей, ноль внешних ссылок.** Всё на Python 3.9+ stdlib
  (`urllib.request`; ни `requests`, ни `jinja2`, ни писателя `.xlsx`). В сгенерированном HTML нет
  `<script src>`, нет внешнего `<link>`, нет `@import`, нет ни одной живой ссылки `http(s)://` —
  проверено механически, не на глаз. Открывается через `file://` без сети, сколько угодно.
